# الرواتب والتعويضات وربط Odoo

## الشاشات

- الإدارة: `/payroll` لإعداد المسير وإرساله واعتماده وصرفه، و`/payroll-compensation` لسياسات GOSI والشرائح وقواعد البنود والمطابقة والقيد وتقدير التصفية.
- الموظف: `/employee/salary` لآخر راتب مصروف وسجل الفترات والاستقطاعات والسلف والقروض وقسائم الراتب والتعريف بالراتب.
- قسيمة عربية قابلة للطباعة والحفظ PDF: `/api/employee/payroll/document?id=<payrollItemId>`؛ قالب HTML عربي يدعم اتجاه RTL والطباعة من المتصفح. المسار القديم `/api/employee/payslip?id=...` يعيد PDF رقميًا ويحترم معرف القسيمة وملكيتها، لكن القالب العربي الموصى به هو قالب الطباعة الجديد.

## النماذج

أُبقيت النماذج الحالية للتوافق بدل تكرار جداول الرواتب:

| الاسم المطلوب منطقيًا | نموذج المشروع |
| --- | --- |
| payrolls | `PayrollRun` للفترة والحالة، و`PayrollItem` لحساب كل موظف |
| payslips | `PayrollItem` مع `payslipIssuedAt` و`calculationSnapshot` |
| advances | `EmployeeSalaryAdvance` و`Loan` |
| gosi_settings | `GosiSetting`، اسم الجدول الفعلي `gosi_settings` |
| salary_rules | `SalaryRule`، اسم الجدول الفعلي `salary_rules` |
| كشوف Odoo الأصلية | `OdooPayrollSnapshot` بمفتاح `(source, odooPayslipId)` |
| طابور الربط المحاسبي | `PayrollAccountingOutbox`، مهمة فريدة لكل مسير |

الترحيل الجديد: `202611050002_payroll_compensation`، يضيف الجداول الجديدة وحقول شريحة التأمينات وأول اشتراك ولقطة الحساب وحصة المنشأة. لا يغير بيانات تاريخية أو يعيد حساب رواتب مصروفة.

`calculationSnapshot` تحتفظ بالمكونات الفردية، المبالغ، العملة، سياسة التأمينات، المراجع المصدرية، وتوزيع الخصومات على القروض والسلف. القسائم والاعتماد والصرف يستخدمون هذه اللقطة. إعدادات السياسات لا تعيد كتابة الرواتب القديمة.

## GOSI

اختيار العميل للسياسة القديمة: **9.75% موظف + 11.75% منشأة = 21.5%**. هذه القيم معبأة في نموذج إعداد السياسة، وليست جدولًا نظاميًا مفروضًا على كل الموظفين.

- يتم الاحتساب للسعوديين فقط حسب `Nationality.code` (`SA`, `SAU`, `SAUDI`) مع اشتراك `ACTIVE`. غير السعودي يحصل على صفر مساهمة ونسب `null` في محرك الرواتب، ولا تعرض القسيمة الجديدة نسبًا له. يجب تصحيح بيانات الجنسية المفقودة قبل احتساب مشترك نشط.
- الخاضع = الأساسي + بدل السكن الخاضع، ثم تطبيق الحدين الأدنى والأعلى من السياسة. لا تُفترض حدود غير معتمدة؛ أدخلها مع تاريخ السريان في شاشة الإعداد.
- الشرائح `LEGACY` و`NEW` أو شرائح مخصصة، بنسب وفترات لا تتداخل للشريحة الواحدة. يدعم الجدول الزيادات المستقبلية بصف لكل فترة دون تعديل الكود.
- `coverageCohort` الصريح هو المرجع الأول؛ وإلا تُشتق الشريحة من **تاريخ أول اشتراك** `firstCoverageDate` وتاريخ الفصل `newSystemCutoff`. لا يستخدم تاريخ التوظيف بديلًا عن أول اشتراك.
- لا توجد نسب جديدة مخترعة أو جدول تصاعدي غير معتمد؛ يُدخل جدول المنشأة المعتمد قبل تفعيل شريحة NEW. السياسة السارية عند نهاية الفترة هي المستخدمة؛ لا توجد تجزئة داخل الشهر.
- حصة المنشأة مصروف منفصل، لا تخصم من صافي الموظف. النسب في سجل التأمينات الإداري القديم لا تتجاوز اختيار السياسة المؤرخة في محرك الرواتب.

## الحساب والاعتماد والصرف

1. يقرأ الحساب مصادر الراتب والبدلات والاستقطاعات والإضافي والمكافآت والحضور والقروض والسلف المستحقة.
2. ينشر الحساب الكامل داخل معاملة واحدة؛ فشل حساب موظف يمنع نشر نتائج جزئية ويمنع الاعتماد حتى إعادة الحساب بنجاح. ملخص أخطاء الحساب في `AppSetting payroll.compute.<runId>`.
3. الاعتماد يثبت الأرقام. التعديل عبر CRUD العام لمسيرات الرواتب أو بنودها موقوف؛ تستخدم شاشة المسير.
4. الصرف لا يعيد الاحتساب، بل يستهلك مصادر اللقطة المعتمدة. تحديث حالة المسير، خصم أقساط القروض والسلف، تعليم الإضافي والمكافآت، إصدار القسائم والتدقيق يحدث داخل المعاملة نفسها.
5. تغير مصدر مالي بعد الاعتماد يرفض الصرف مع التراجع عن جميع الآثار. اعتماد أو صرف متزامن لا يستهلك المصدر مرتين.
6. البنود غير المتكررة لها علامات استهلاك فريدة `payroll.once.allowance.<id>` و`payroll.once.deduction.<id>`؛ إعادة صرفها ترفض المعاملة. المسيرات المستوردة لا يعاد احتسابها من مصادر محلية.

لا يمثل تغيير حالة المسير إلى PAID دليلًا على استجابة البنك؛ هو تسجيل إداري للصرف، ويحتاج مطابقة الصرف الفعلي حسب إجراءات المالية.

## Odoo: السحب والمطابقة والقيد

يستخدم الموصل عميل المشروع الحالي الداعم JSON-RPC/XML-RPC، مع التحقق من حقول الإصدار عبر `fields_get`:

- قراءة كشوف المسودة والمنتهية وغيرها، وترقيم `id > lastId` و`order id asc` وبحزم 500 مع `active_test:false`.
- قراءة كل `hr.payslip.line` بما فيها `id`, `code`, `name`, `quantity`, `rate`, `amount`, `total`, `salary_rule_id`, `category_id` عند توفرها. مقارنة معرفات البنود و`write_date` قبل الحفظ تمنع قبول كشف جزئي أو تغير أثناء القراءة.
- خطأ كشف لا يسقط بقية الكشوف؛ يعاد عدد المستورد والمتجاوز والأخطاء دون تسجيل بيانات الرواتب الخام.
- لا تحويل للبنود إلى بدلات متكررة، ولا كتابة صافي افتراضي عند فشل قراءة البنود. `OdooPayrollSnapshot` يحفظ رأس الكشف وبنوده الأصلية.
- الاستيراد إلى مسودة HRMS خطوة صريحة. تُصنّف جميع الرموز عبر `SalaryRule`، مع التحقق من توافق الأساسي + البدلات = الإجمالي، والإجمالي − الخصومات = الصافي. الرموز المجهولة أو كشف ثانٍ للموظف في المسير نفسه لا تُجمع ولا تُستبدل تلقائيًا.
- متعدد كشوف الموظف يحتفظ به في snapshots؛ النموذج الحالي `PayrollItem` يسمح بكشف واحد لكل موظف في المسير، ولذلك يلزم اختيار الكشف المقصود بدل فقد التفاصيل بتجميع صامت.
- عملة الكشف تُقرأ من Odoo أو من شركة الكشف؛ لا تفترض SAR. مصدر Odoo معرف ببصمة URL/قاعدة البيانات بلا أسرار.

عند الاعتماد، تسجل مهمة outbox في المعاملة المحلية نفسها ثم تحاول الربط. فشل الاتصال يبقي المهمة قابلة للمراجعة وإعادة المحاولة، ولا يدعي نجاحًا محاسبيًا خارجيًا:

### RECONCILE — المسيرات المستوردة

قراءة `hr.payslip.move_id` والتحقق من اعتماد الكشف، وترحيل `account.move`، ومطابقة صافي الراتب والموظف. تحفظ مراجع القيود في نتيجة المهمة. لا تعيد إنشاء قيد Odoo الأصلي.

### POST_JOURNAL — المسيرات المحلية

يتطلب إعدادًا صريحًا للشركة والدفتر والعملة وحساب مصروف الرواتب والاستقطاعات والرواتب المستحقة ومصروف/التزام تأمينات المنشأة. لا توجد أرقام حسابات مفترضة.

يبني سطرًا لكل مكون من لقطة المسير، مع فصل تأمينات المنشأة، ويتحقق من توازن المدين والدائن والعملة والشركة والدفتر. ينشئ ويرحّل `account.move` بمرجع ثابت `LANA-PAYROLL-<runId>`.

الكتابات المالية تستخدم عميلًا بلا إعادة محاولة عمياء. إذا ضاع رد الإنشاء، تعيد المحاولة البحث بالمرجع وتتحقق من السطور والدفتر والتاريخ قبل إكمال الترحيل، ولا تنشئ قيدًا ثانيًا. المرجع الموجود غير المطابق أو المتعدد يتطلب مراجعة محاسب. الحسابات هنا مجمعة حسب نوع الاستحقاق/الخصم مع إبقاء كل سطر مفصلًا؛ توزيع الحسابات حسب كل قاعدة/مركز تكلفة أو إنشاء مسودات `hr.payslip` جديدة يحتاج خريطة محاسبية خاصة بالمنشأة.

إعداد الاتصال يعيد استخدام ODOO_* أو اتصال Odoo المحفوظ. عند تعدد الاتصالات يجب تحديد `connectionId` في إعداد القيد، دون اختيار حساب آخر بصمت. لم يُنفذ اختبار حي أو ترحيل على Odoo فعلي في هذه المهمة؛ الاختبارات تستخدم موصلًا تجريبيًا، بما فيه فقدان الرد بعد إنشاء القيد.

## التقارير والمستندات

- تعرض شاشة الموظف الرواتب المصروفة فقط (`paidAt` موجود وحالة PAID/LOCKED/ARCHIVED)، وتفصل العملات ولا تعتبر المسودات مبالغ مصروفة.
- القسيمة المختارة تعرض بنود اللقطة والخصومات والإجمالي والصافي وتفاصيل GOSI المؤهلة. كل مسار يتحقق من ملكية الموظف؛ معرف قسيمة موظف آخر يرجع 404.
- تعريف الراتب مع البدلات أو بالأساسي فقط، موجه لجهة يحددها الموظف. يتطلب طلب `LETTER` نوع `salary` معتمدًا عبر الخدمات الذاتية.
- QR يحمل مرجع المستند فقط؛ ليس رابطًا عامًا يكشف الرواتب، وليس شهادة تحقق بنكية.
- التوقيع صورة مفوضة (PNG/JPEG data URL) واسم مفوض من إعدادات `payroll.certificateSignatureDataUrl` و`payroll.certificateSignatory`. عند غيابها تطبع النسخة **غير موقعة** بوضوح. هذا توقيع مرئي، وليس توقيع PKI رقميًا.

## EOSB والتصفية

المحرك يدعم نصف شهر لكل سنة من السنوات الخمس الأولى وشهرًا لما بعدها، مع شرائح الاستقالة (قبل سنتين صفر، 2–أقل من 5 ثلث، 5–أقل من 10 ثلثان، 10 فأكثر كامل). عدم التجديد/الإنهاء يحتسبان الأصل كاملًا، مع مدخل HR مستقل للمادة 80 والاستثناءات المعتمدة.

التقدير يستخدم الأيام الفعلية ÷ 365 ويقبل الأيام المستبعدة والأجر الشهري المعتمد؛ لا يصدر قرارًا قانونيًا آليًا. إجمالي التصفية يجمع المكافأة والرواتب غير المصروفة ومقابل الإجازة والمستحقات الأخرى، ويطرح الخصومات وأرصدة السلف المدخلة والمراجعة. الناتج يحتاج مراجعة الموارد البشرية ولا يطلق تحويلًا ماليًا.

## البنك وWPS

حسب رد العميل، البنك والمواصفات سيحددان لاحقًا. `bank-review` يصدر CSV مراجعة يحتوي الموظف وIBAN والعملة والصافي، ويتحقق من IBAN سعودي بخوارزمية MOD97، وحساب رئيسي واحد، وعملة SAR ومبالغ موجبة، ويمنع CSV formula injection. **ليس ملف WPS/MOL معتمدًا ولا يُرسل للبنك.** محول البنك النهائي ينتظر مواصفاته.

## API

| المسار | الوظيفة |
| --- | --- |
| GET `/api/employee/payroll?page=1` | الرواتب المصروفة والمجاميع حسب العملة والقروض والسلف |
| GET `/api/employee/payroll/document?id=...&kind=certificate&details=1&recipient=...` | قالب طباعة عربي للقسيمة/التعريف |
| GET/POST `/api/enterprise/payroll/compensation` | السياسات، ربط الشريحة، قواعد البنود، خريطة الحسابات وتقدير EOSB/التصفية |
| GET/POST `/api/enterprise/payroll/odoo` | عرض snapshots؛ actions: pull/materialize/reconcile/post-journal |
| GET `/api/enterprise/payroll/bank-review?runId=...` | CSV مراجعة مصرفية لمسير معتمد |
| PATCH `/api/enterprise/payroll/run/:id` | submit/approve/pay وغيرها مع حماية الأرقام والمصادر |

الإدارة المحاسبية والسياسات والترحيل محمية بصلاحيات اعتماد الرواتب (`SUPER_ADMIN`/`HR_MANAGER`) الحالية. إدارة المسودات تستخدم صلاحيات الرواتب القائمة. لا تمنح الواجهات المالية صلاحية جديدة لموظف عادي.

## التحقق قبل النشر

```sh
npx prisma generate
npm run typecheck
npm run build
node --experimental-vm-modules tests/payroll/calculations.test.mjs
node --experimental-vm-modules tests/payroll/odoo.test.mjs
node --experimental-vm-modules tests/payroll/journal.test.mjs
PAYROLL_TEST_DATABASE_URL='postgresql://…@localhost:5432/lana_self_service_test' node --experimental-vm-modules tests/payroll/settlement.integration.mjs
```

الترحيل الجديد اختُبر على قاعدة PostgreSQL محلية مستقلة فقط. ما زالت ملاحظة انحراف الترحيلات القديمة عن `User.sidebarHue` قائمة كما في دليل الخدمات الذاتية. يجب مراجعة مخطط بيئة النشر قبل تنفيذ migrate deploy؛ لم تُعدّل قاعدة إنتاج ولم يُنشر شيء ولم تُرسل قيود أو رواتب إلى خدمة خارجية.

نتائج التحقق الحالية: نجح TypeScript والبناء وESLint للملفات المعدلة و50 اختبارًا لمحركات الطلبات والرواتب. نجح أيضًا اختبار PostgreSQL للصرف واختبار Chromium للوحة الموظف والقسيمة العربية والحفظ PDF وتعريف الأساسي فقط ومنع قسيمة الغير ومنع الموظف من إعدادات الإدارة. اختبار المتصفح القابل للإعادة: `tests/payroll/portal.integration.mjs`؛ يحتاج خادم اختبار محلي على المنفذ 3200 بمفتاح جلسات اختبار مؤقت، و`PAYROLL_TEST_DATABASE_URL` المحلي و`PAYROLL_TEST_AUTH_SECRET_FILE` لمسار ذلك المفتاح فقط. لا تستخدم مفاتيح إنتاج لهذا الاختبار.
