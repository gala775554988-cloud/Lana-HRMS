# المزامنة الشاملة من Odoo إلى LANA-HRMS

## التشغيل والواجهات

لوحة الإدارة: `/odoo-migration`، مرتبطة بلوحة `/payroll-compensation`. تتطلب صلاحية اعتماد الرواتب الحالية (`SUPER_ADMIN` أو `HR_MANAGER`). تتضمن زر البدء، نسبة تقدم، نسبة نجاح السجلات المفحوصة، آخر معرف وصفحة وشهر، وإيقافًا مؤقتًا واستئنافًا وإلغاءً وإعادة محاولة لكل خطأ.

التشغيل أحادي الاتجاه **Odoo → LANA**، ولا يستدعي `create/write/action_post` في Odoo. لا ينشر التطبيق ولا يرسل رواتب أو قيودًا. إنشاء الوظيفة لا يشغل خدمات خلفية غير مضمونة؛ الواجهة ترسل دفعات HTTP متسلسلة، كل طلب حتى 500 سجل مع ميزانية عمل محدودة و`maxDuration=300`. إغلاق الصفحة يوقف الدفعات التالية، مع إمكانية المتابعة من نقطة الحفظ. لا Redis أو BullMQ أو طابور خارجي.

يمكن التشغيل من CLI مستقل (ليس ضمن build أو seed تلقائي):

```sh
npx --no-install tsx scripts/odoo-history-sync.ts start /path/to/mapping.json <authorizedActorUserId>
npx --no-install tsx scripts/odoo-history-sync.ts resume <jobId> <authorizedActorUserId>
npx --no-install tsx scripts/odoo-history-sync.ts status <jobId> <authorizedActorUserId>
```

يتحقق CLI من حساب HR مفوض ونشط. يطبع معرف التشغيل والمرحلة والعدادات فقط، ولا يطبع بيانات الموظفين أو الأسرار. يعيد exit code غير صفري عند الأخطاء أو عدم اكتمال المعالجة.

## المراحل

1. **EMPLOYEES**: الاسم والرقم الوظيفي والهوية والقسم والمسمى والشركة وتاريخ التعيين والحالة الاجتماعية والجنسية والنشاط وسبب المغادرة.
2. **MANAGERS**: ربط المدير بعد استيراد الموظفين، حتى لو ظهر المدير في دفعة لاحقة. لا يغير الموظفين الذين تعارضت هوياتهم أو لم يكتمل استيرادهم.
3. **LOANS**: السلف والأصل والرصيد والحالة والعملة وكل قسط، مع حالة سداد المصدر وحالة الخصم المحلي.
4. **PAYROLL**: كشوف التاريخ شهرًا بشهر، وكل بند بقيمته وكميته ونسبته وإجماليه ومراجع قاعدته الأصلية.

جميع الصفحات تستخدم `id > lastOdooId`, `order id asc`, `context:{active_test:false}` وحجم 500. يثبت الحد الأعلى للمعرفات عند بدء المرحلة. يخزن بعد الدفعة الصفحة والمؤشر وآخر write_date والعدادات. الأخطاء الفردية لا توقف بقية السجلات؛ أخطاء النموذج/الصلاحيات/الاتصال تمنع إعلان اكتمال المرحلة.

قفل عامل بمهلة مع fencing داخل معاملات الكتابة يمنع تشغيل عاملين للوظيفة نفسها أو الكتابة بعد الإيقاف. فهرس فريد جزئي يمنع وظيفتين نشطتين للمصدر نفسه. إعادة الصفحات بعد انقطاع آمنة بالمفاتيح الأصلية والـ checksums. عدادات الواجهة تمثل السجلات/المراحل المعالجة، وتشمل مرور ربط المدراء؛ ليست عدد الموظفين الفريدين فقط.

## خريطة Odoo القابلة للضبط

لا يوجد نموذج سلف موحد في جميع إضافات Odoo. يفحص الموصل `fields_get` قبل القراءة ويتوقف بوضوح عند نقص النموذج أو الحقول. مثال إعداد (بلا كلمات مرور):

```json
{
  "connectionId": "existing-odoo-connection-id",
  "employeeNumberField": "barcode",
  "nationalIdField": "identification_id",
  "hireDateField": "first_contract_date",
  "loanModel": "hr.loan",
  "loanFields": {
    "employee": "employee_id",
    "principal": "loan_amount",
    "balance": "balance_amount",
    "state": "state",
    "currency": "currency_id",
    "date": "date",
    "lines": "loan_lines"
  },
  "installmentFields": {
    "loan": "loan_id",
    "date": "date",
    "amount": "amount",
    "paid": "paid"
  },
  "loanStateMap": {
    "draft": "PENDING",
    "waiting_approval_1": "PENDING",
    "waiting_approval_2": "PENDING",
    "approve": "ACTIVE",
    "close": "PAID",
    "cancel": "CANCELLED"
  },
  "departureReasons": { "1": "RESIGNED", "2": "DISMISSED" },
  "fromMonth": "2020-01",
  "toMonth": "2026-11"
}
```

الأرقام في `departureReasons` أمثلة فقط؛ يجب أن تطابق معرفات الأسباب الفعلية لدى المنشأة. ويمكن استخدام `employeeStatusField` و`employeeStatusMap` لحقول حالة مخصصة. لا تُستنتج الاستقالة أو الفصل من `active=false` وحده: يظل الموظف INACTIVE إن لم توجد خريطة معتمدة، مع الاحتفاظ بحالة المصدر وسببها.

عند غياب الفترة يبدأ من أول شهر فعلي في المصدر حتى الشهر الحالي. يعاد استعمال ODOO_* أو اتصال Odoo المحفوظ؛ عند تعدد الاتصالات يلزم اختيار واحد. لا تُطلب كلمات المرور في حقول JSON. بصمة URL/اسم قاعدة المصدر تحدد source دون تضمين بيانات اعتماد. يربط أول تشغيل مصدر الموظفين في إعداد `odoo.migration.employeeSource`؛ تغيير المصدر يحتاج مراجعة مطابقة مستقلة.

تاريخ التعيين والهوية والرقم الوظيفي حقول مطلوبة للاستيراد. لا تُختلق هوية أو يستخدم `hr.employee.id` رقمًا وظيفيًا. عند فقدها يحفظ خطأ واضح لإصلاح المصدر/الخريطة ثم إعادة المحاولة. ربط الجنسية يستخدم رمز `res.country.code` لتحديد السعودية بدقة في محرك الرواتب.

## نماذج قاعدة البيانات

الترحيل: `202611050003_odoo_historical_migration`.

| المفهوم | التخزين |
| --- | --- |
| الموظفون | `Employee` والجداول المرجعية الحالية |
| السلف | `Loan` مع `(odooSource, odooLoanModel, odooLoanId)` فريد |
| أقساط السلف | `OdooLoanInstallment` مع `(loanId, externalId)` فريد |
| مسرد تاريخي | `HistoricalPayrollRun` حسب المصدر والشركة والشهر ومعرف المسرد الأصلي |
| قسيمة تاريخية | `HistoricalPayslip` مع `(source, odooPayslipId)` فريد |
| بنود القسيمة | `HistoricalPayslipLine` مع `(payslipId, externalId)` فريد |
| نقاط الاستئناف | `OdooMigrationJob` |
| أخطاء السجلات | `OdooMigrationError` مع `(jobId, entity, externalId)` فريد |
| أصل بيانات المصدر | `OdooSourceRecord` مع source/entity/externalId وchecksum وraw ومرجع السجل المحلي |

لا تكرر الهوية أو البريد أو الرقم الوظيفي ولا تُدمج الحسابات المتعارضة. التعارض يسجل خطأ ويتجاوز الحساب دون تعديله. لا تحذف البيانات المحلية التي لم تظهر في Odoo تلقائيًا، ولا يعاد ربط سلفة/قسيمة بموظف آخر إذا تغير المالك.

النسخ raw في جداول المصدر مخصصة لإعادة المعالجة والتدقيق المقيد؛ لا تظهر في أخطاء الواجهة أو السجلات العامة. سجلات AuditLog تحمل المعرفات والمرحلة والعدادات والإجراء، دون أسماء أو هويات أو مبالغ خام. واجهات الإدارة لا تعرض مفاتيح القفل أو أسرار الاتصال.

## المصالحة المالية

تُحوّل قيم المصدر إلى وحدات صحيحة بدقة ست منازل عبر BigInt أثناء التحقق، ثم تخزن نصًا/Decimal(20,6). تُرفض المنازل الزائدة أو القيم غير الصالحة بدل التقريب. المقارنة على القيم التي يعيدها موصل Odoo؛ لا تعيد إنشاء دقة لم يرسلها المصدر.

### الرواتب التاريخية

- يجب اكتمال معرفات `line_ids` واتفاق `write_date` قبل وبعد القراءة.
- تحفظ جميع البنود، بما فيها المعلوماتية وحصة المنشأة، دون إسقاطها أو تحويلها إلى بدلات متكررة.
- BASIC/GROSS/NET تصنيفات افتراضية. بقية الرموز تتطلب `SalaryRule` معتمدًا من `/payroll-compensation`؛ المجهول يبقى خطأ يحتاج خريطة.
- يتحقق الأساسي + البدلات = الإجمالي، والإجمالي − الاستقطاعات = الصافي بدقة المصدر، دون هامش إخفاء لفروقات أصغر من الهللة.
- مصدر الكمية والنسبة والقيمة والإجمالي ومراجع القاعدة والتصنيف محفوظ في كل سطر، بما فيه إشعار الائتمان `credit_note` عند توفره في رأس الكشف.
- يمكن حفظ عدة كشوف للموظف في الشهر نفسه. لا يطبق قيد المسير التشغيلي «كشف واحد للموظف» على التاريخ ولا تُجمع الكشوف لإخفائه.
- الكشف المعتمد/المسدد لا يستبدل تلقائيًا إذا تغيرت أرقامه أو خطوطه أو الشركة/الفترة/المالك. يحفظ المصدر الجديد للمراجعة ويظهر `FINALIZED_HISTORY_CHANGED`. يمكن ترقية الحالة done إلى paid إذا بقيت البيانات المالية نفسها.
- لا ينشأ `PayrollItem` تشغيلي أو طلب صرف أو قيد محاسبي جديد أثناء ترحيل التاريخ. حالة done تعني معتمدًا فقط، ولا تعتبر مدفوعًا.

### السلف والأقساط

للسلفة ذات الجدول: مجموع الأقساط = الأصل، والأصل − أقساط Odoo المسددة = الرصيد. حالة paid تتطلب رصيد صفر، وactive تتطلب رصيدًا موجبًا. السلفة المعلقة قبل إنشاء جدولها مقبولة إذا كان رصيد المصدر صفرًا أو يساوي الأصل، وتظل PENDING ولا تخصم.

المبالغ التشغيلية في نموذج Loan الحالي بدقة هللتين؛ إذا كانت مبالغ السلفة تحتاج أكثر من ذلك يرفض الاستيراد التشغيلي بدل تقريب الدين. تاريخ الرواتب وبنوده يحتفظ بست منازل.

محرك الرواتب يختار أقساط السلفة المستوردة غير المسددة والمستحقة داخل فترة الراتب فقط، ويتحقق من العملة والرصيد. الصرف يحفظ `localPaidAt` داخل معاملة الخصم نفسها. إعادة المزامنة تخصم من رصيد Odoo الأقساط التي خصمت محليًا ولم يؤكدها المصدر بعد؛ وعندما يؤكد Odoo السداد لا يخصم الرصيد مرة ثانية. تغيير/حذف قسط خصم محليًا أو التراجع عن سداد مؤكد يحتاج تسوية، ولا يمحى أثره تلقائيًا. تعديل/حذف السلفة المستوردة عبر CRUD العام محظور.

لا ترسل خدمة السحب تأكيد السداد المحلي إلى Odoo؛ المطابقة تحفظ الطرفين حتى يتحدث المصدر عبر إجراء المالية المعتمد. لا يعاد خصم الأقساط التاريخية عند قراءة قسيمة قديمة.

## واجهات API

| الطريقة والمسار | الغرض |
| --- | --- |
| GET `/api/enterprise/odoo-migration` | أحدث 20 تشغيلًا |
| POST `/api/enterprise/odoo-migration` | إنشاء تشغيل بخريطة معتمدة وفترة اختيارية |
| GET `/api/enterprise/odoo-migration/:id` | التقدم والحالة وأحدث 50 خطأ مفتوحًا |
| POST `/api/enterprise/odoo-migration/:id` | `{action: step|pause|resume|cancel}` |
| POST `/api/enterprise/odoo-migration/:id` | `{action: "retry", errorId: "..."}` |
| GET `/api/employee/payroll/history?page=1` | كشوف الموظف التاريخية المعتمدة/المسددة، مع تحقق الجلسة والملكية |
| GET `/api/employee/payroll/history/document?id=...` | بنود قسيمة تاريخية عربية قابلة للطباعة والحفظ PDF |

تعرض شاشة `/employee/salary` التاريخ المستورد بشكل مستقل عن الرواتب المصروفة محليًا. لا تخلط المبالغ أو العملات ولا تجعل التاريخ يستهلك مصادر تشغيلية.

## الاستئناف ونسبة النجاح

التقدم موزع على مراحل المعالجة ويصل 100% عند انتهاء القراءة، حتى لو بقيت أخطاء؛ تظهر الحالة حينها **COMPLETED_WITH_ERRORS**. نسبة النجاح تحسب من السجلات المفحوصة والأخطاء المفتوحة. ليست نسبة تصديق على منشأة لم تختبر بعد.

الأخطاء الفردية قابلة لإعادة المحاولة بعد إصلاح مصدرها أو ربط الموظف/قاعدة الراتب. يمكن إيقاف التشغيل قبل إعادة المحاولة. تتجدد قائمة أحدث 50 خطأ عند حلها حتى تظهر الأخطاء الأقدم. الأخطاء المتعلقة بالنموذج نفسه تحتاج صلاحيات أو خريطة صحيحة؛ عند تغيير نموذج/خريطة جوهرية ابدأ تشغيلًا جديدًا بعد إلغاء القديم، ولا تغير اتصال وظيفة قائمة بصمت.

تغير عدد السجلات أثناء المرحلة يمنع إعلان اكتمال مصالحة تلك المرحلة. المصدر ليس لقطة ذرية موحدة عبر كل Odoo؛ تؤخذ حدود المعرفات عند بدء المرحلة ويُراجع كل كشف/سلفة أثناء القراءة. التعديلات على سجلات خلف مؤشر اجتازته وظيفة تستلزم تشغيل تحقق جديدًا. قبول الترحيل المالي الفعلي يحتاج صفر أخطاء مفتوحة ومراجعة عينات ومطابقة دفاتر المنشأة؛ لا تدّعي الخدمة تطابق 100% قبل ذلك.

## الاختبارات

```sh
npx prisma generate
npm run typecheck
npm run build
node --experimental-vm-modules tests/odoo-migration/mapping.test.mjs
ODOO_MIGRATION_TEST_DATABASE_URL='postgresql://…@localhost:5432/lana_self_service_test' node --experimental-vm-modules tests/odoo-migration/service.integration.mjs
```

اختبار التكامل يستخدم Odoo تجريبيًا ولا يكتب إلى نظام خارجي. يغطي 501 موظفًا، قفل عاملين متزامنين، دفعات 500 والاستئناف، هويات مكررة، الاستقالة وربط المدير، إعادة محاولة سجل، سلفة معلقة، جدول أقساط وخصم محلي ومطابقة لاحقة، 1003 بنود لكشف واحد، كشفين للموظف في شهر واحد، حماية التاريخ المعتمد، وعدم إنشاء مسير صرف من التاريخ. التنظيف محصور ببيانات الاختبار في قاعدة محلية ينتهي اسمها بـ `_test`.

الترحيل اختُبر على قاعدة محلية مستقلة. لم تُستخدم بيانات اعتماد Odoo فعلية ولم يُسحب تاريخ حقيقي أو تُعدل قاعدة إنتاج أو يُنشر التطبيق. ما زالت ملاحظة انحراف الترحيلات القديمة عن `User.sidebarHue` موثقة في أدلة الوحدات السابقة، وتحتاج مراجعة بيئة النشر قبل الترحيل.

نتائج التحقق: نجح البناء وفحص الأنواع وESLint للملفات المعدلة، و53 اختبارًا لمحركات الطلبات والرواتب والمزامنة. نجح اختبار PostgreSQL الشامل أعلاه، واختبار المتصفح `tests/odoo-migration/portal.integration.mjs` الذي تحقق من التقدم والتحكم والصلاحيات 401/403 وعدم كشف مفاتيح القفل، وقائمة التاريخ وقسيمة PDF عربية ومنع قسيمة الغير وعدم وصف الكشف المعتمد بأنه مدفوع. اختبار المتصفح يحتاج خادم اختبار محلي على 3200، ومفتاح جلسات اختبار مؤقت في `PAYROLL_TEST_AUTH_SECRET_FILE`، وقاعدة `ODOO_MIGRATION_TEST_DATABASE_URL` المحلية المعزولة؛ لا تستخدم مفاتيح إنتاج.

سكربت CLI يعطل إصلاح المخطط التلقائي بضبط `SKIP_AUTO_DDL=true` قبل تحميل عميل المشروع، ويؤخر تحميل قاعدة البيانات حتى بعد معالجة `--help`؛ تُطبَّق ترحيلات المخطط صراحة، ولا يُعتمد على إصلاح المخطط القديم أثناء تشغيل ETL. وضع `--help` اختُبر دون استعلامات قاعدة بيانات.
